# Candidate computational world: design after three research cycles

5 November 2026, America/Chicago. **Proposal only: no interpreter built, installed or activated.** This proposal incorporates three scouts’ final cross-review; see cycle reports and the decision log in REPORT.md. The old garden remains a separate preserved season at entry 500.

## Purpose

A persistent computational medium in which an agent can construct, execute, inspect, revise and reuse algorithms. Domain abstractions are ordinary programs/data within that medium. Optional seeds offer directions, not a required sequence of projects. A run ends because its activity budget ends, not because the world is discarded. Operational freedom is defined by effective actions, not an invitation alone.

## 1. Language and machine are different layers

Leading candidate: a small Lisp-like expression language with explicit parameters and positional arguments. Its implementation uses an explicit evaluator state and deterministic transitions. Assembly is a possible debug representation, not the proposed authoring interface. This is a bespoke dialect, not full Scheme or Forth; no compatibility or theoretical minimality claim.

Core values: exact integers with a declared bit-size cap, Booleans, Unicode text and finite nested lists. Identifiers are source syntax, distinct from runtime strings; runtime symbols and quotation are deferred. Tags can be text values inside lists. Define Unicode indexing, equality, arithmetic and serialization before implementation. Reject overflow/oversize explicitly; never silently wrap or clamp. Avoid floats initially. This numeric choice is provisional, not empirically superior to signed fixed-width values.

Core expressions: literals, variable lookup, `if`, local `let`, application of a named versioned procedure, arithmetic/comparison, list constructors/selectors (including `list`, `head`, `tail` and `empty?`), and text length/slicing/concatenation. Only the chosen `if` branch evaluates. Otherwise specify left-to-right evaluation. Keep constructors/accessors explicit and type errors observable. Named procedures may recurse, consuming the same budgets. General recursion does not grant unlimited runtime. First-class closures, dynamically executing data, macros, mutual recursive groups and concurrency are deferred features, not silently implied by calling the surface Lisp-like.

## 2. Durable world

World artifacts include data values, procedure source and dependencies, notes, and execution receipts. Objects and revisions have immutable IDs. A human-readable name points to a revision; changing the name's target does not mutate previous source or receipts. Explicit arguments and pinned dependency revisions prevent a helper edit from silently changing an older procedure. A self-recursive binding resolves to that same procedure revision; multi-procedure cycles require an explicit later design. Store and retrieve partial drafts as data even when they do not parse as programs.

A run receives explicit inputs resolved from a recorded world snapshot. Its computational core is pure: no hidden access to host files, network, clock, model internals or ambient mutable state. A program can transform a structured representation of its own project or simulation state and return the next representation. Each invocation declares pure `run` or `run-and-publish`. Pure `run` returns a bounded result and host receipt without a guest artifact. `run-and-publish` stages the result for an atomic artifact publication and any declared alias update. A later publish action must resubmit bounded canonical data; no unlimited staging cache is implied. Defining/revising a valid procedure is itself a durable publication; incomplete drafts stay ordinary data. Thus stateful algorithms can be represented explicitly across calls without unrestricted host effects. Later effectful capabilities would require versioned semantics and a separate evaluation.

The model can inspect artifacts, create data, define or revise procedures, run expressions/procedures, publish successful results and write notes. These are generic operations, not a catalog of allowed subjects. Listing and paginated lookup expose discoverable procedure signatures, revisions, dependencies and source. Small edits and short calls support incremental work within the model's output limit. The exact command syntax and edit operations remain an implementation decision to test, not a frozen command grammar.

## 3. Execution and resource contract

For each invocation record expression/procedure and dependency IDs, inputs, world snapshot ID, evaluator/cost versions and all limits. Check submission bytes/depth before expensive parsing. Maintain explicit control/continuation state rather than relying on unbounded host recursion. Count specified evaluator transitions and bound intermediate allocation, integer size, frames, output and persistent bytes separately. Size-dependent primitives must check/reserve conservative work/allocation bounds before work or execute bounded elementary transitions. Parsing, validation, hashing, serialization, observation and durable writes have separate bounds; evaluator fuel alone does not cover them. Exact transition counts describe this machine, not exact CPU time; independent process/time limits address host faults.

Normal pure completion returns `COMPUTED`. Normal completion in the declared publish mode stages a candidate result. A host-owned serialized commit validates quotas and atomically records artifact revision, declared alias update and receipt before returning `PUBLISHED`. Publication rejects unresolved dependencies and captures immutable revisions. Invocation resolves friendly aliases from its recorded snapshot before evaluation; procedure calls cannot dynamically follow later aliases. Alias updates require the expected prior revision.

Syntax/type/arithmetic/limit errors publish no successful result and change no existing artifacts. Before admitting an action reserve bounded host-ledger receipt capacity that guest artifacts cannot consume. On failure discard staged effects and record a bounded diagnostic receipt. If storage fails, report a host outcome with commit certainty known or unknown; reconcile unknown outcomes by request ID. A repeated request ID returns its existing outcome rather than rerunning or duplicating publication. Do not equate an exception with a completed rollback.

Per-action limits are supplemented by finite per-visit/experiment totals for actions, model tokens, evaluator work, observations, artifacts and audit bytes. Distinguish per-procedure source size, reachable dependency size and total library capacity. Stop admission when the receipt reserve is exhausted; retain existing history. The agent can revise or remove friendly names and compact its own data, but pinned dependencies and historical receipts remain immutable. Removing a name does not guarantee reclaiming retained revision bytes. Before implementation specify export/retention and reachability policies; stop visibly at a quota rather than silently pruning projects or erasing history.

Out-of-fuel means incomplete under that allowance, not false, divergent or incapable. V1 proposes no automatic serialization of a mid-execution VM. Completed procedure/data artifacts persist. A long computation can intentionally finish a chunk and publish its progress as ordinary data, then continue from that checkpoint in a later call; exhaustion itself does not save partial success. This limitation must be visible. An operational pause happens between committed actions; freezing world time does not imply capturing a running computation. Host aborts are infrastructure outcomes, not model-task failures.

No numerical quota is adopted here. Select provisional bounds from host tests and measured prompt/output behavior, record them, and change them only as explicit experimental interventions. Bounded deployed state is finite; do not advertise literal unbounded universality or the ability to decide all program properties.

## 4. Observation and seeds

Return a compact machine-derived receipt: status, result/error, source location when available, resource use, and committed artifact IDs. Keep a bounded trace inspectable on demand with explicit truncation markers. Support pagination and stable lookup; a large durable store is not useful if its index cannot fit or be queried. Separate user-facing summaries from host audit records. No requirement to provide a rationale before a valid action can execute.

Seed examples could be data exhibiting a pattern, a small program with a surprising result, or the concept of symmetry. Their provenance, initial-state artifacts/aliases, wording and timing are recorded. A no-seed comparison excludes seed-only artifacts, aliases and tools, while sharing language primitives. Separate any required onboarding from subsequent free-choice activity. A sequence does not have a unique next value without assumptions; a self-reported pattern is a hypothesis until tested. Seeds need not unlock rewards or obligate completion. Inspecting, ignoring, editing, returning to a seed and pursuing another project remain available choices.

The public language/rule reference and current resource limits are inspectable. Host knowledge of execution mechanics does not mean predicting all program behavior or knowing the model's internal reasoning. Evidence for a scientific domain claim needs appropriate external grounding; a successful program run validates its computation under these semantics.

## 5. Three design walkthroughs — pseudocode, manually reasoned and not executed

**Construct and reuse.** Define `twice@1(x) = (+ x x)`; run with 3 and publish result 6. Define `four@1(x) = (twice@1 (twice@1 x))`; input 3 gives 12. The explicit `@1` calls denote pinned dependency bindings, not text looked up at runtime. Rebinding the label `twice` to a different new revision must not change `four@1`. Later code may explicitly adopt that revision. This illustrates compositional persistence, not observed model discovery.

**Fail and repair.** Define `first@1(xs) = (head xs)` and run on empty list: a typed empty-list error with no result artifact. Save `first@2(xs) = (if (empty? xs) (list "absent") (list "present" (head xs)))`. Empty input returns `["absent"]`; input `[7]` returns `["present", 7]` in illustrative result notation. Only the selected branch evaluates. A usable error plus a working revision would be behavioral evidence; the explanation alone would not be.

**Continue an unfinished project.** For a doubling project, a chunk procedure accepts `[remaining, output]`, processes one head, appends twice its value and returns the new pair. Starting `[[2,3], []]`, successful chunks produce `[[3], [4]]` and then `[[], [4,6]]`. Publish the first pair as an ordinary checkpoint artifact; the second call consumes it as explicit input. Store its procedure revision with the checkpoint. Pause between actions. Reload the identical world; retrieve the same program and checkpoint IDs and process the next chunk. A different example that simply exhausts fuel must produce no new checkpoint. Compare uninterrupted versus chunked computation under pinned semantics; equality is a future test, not a result here.

## 6. Acceptance work before a model pilot

Host tests must cover parsing bounds, types/evaluation order, numeric/text boundary rules, dependency versioning and recursion, expensive primitives, failure atomicity, receipt reserves, artifact paging, idempotent request handling, save/reload/replay equality and explicit checkpointing. Use a separately simple reference for tiny expressions, action-sequence testing and bounded enumeration where practical. Passing a finite test set is not a correctness proof.

After host checks, use isolated matched-budget small-model trials: literal action/lookup, one expression, one named procedure, composition, feedback-based repair, and reuse across a context boundary. Compare compact direct syntax with a syntax aid if needed. Include seed-free time and do not require every run to yield a construction. Record parser validity, effects, actual result correctness, retry changes and durable reuse separately. No weights, adapter or primary state change is part of this design scout.
