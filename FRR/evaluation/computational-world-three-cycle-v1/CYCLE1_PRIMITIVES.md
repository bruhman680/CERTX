# Cycle 1: compositional computational primitives

Research/design only, 5 November 2026 client date (host UTC 6 November). No model, installation, execution experiment, or primary-run access. The recommendations below are interpreter-design inferences, not evidence that a CPU 135M+LoRA model can exploit them.

## Primary sources and read depth

1. [R7RS-small Scheme report (2013)](https://small.r7rs.org/attachment/r7rs.pdf): selectively read §3.5 proper tail recursion; §4.1 variable/literal/call/lambda/conditional/assignment semantics; §6.4 pair/list representation; selected §6.7 string operations. Not a full report or formal-semantics audit. Calls explicitly supply arguments; lambdas capture lexical environments; quotation separates data from execution. Pairs recursively build lists. Tail calls avoid accumulating return continuations. Crucial caveat: Scheme leaves argument evaluation order unspecified; a new bounded dialect should specify it. A deliberately restricted dialect should not claim R7RS conformance.
2. [Forth standard core glossary](https://forth-standard.org/standard/core), specifically normative entries [DUP](https://forth-standard.org/standard/core/DUP), [colon definitions](https://forth-standard.org/standard/core/Colon), [IF](https://forth-standard.org/standard/core/IF), and [RECURSE](https://forth-standard.org/standard/core/RECURSE): read the entries' stack effects, execution/compilation semantics, and recursion example, excluding community discussions as authority. Words compose through a shared operand stack; definitions name sequences. IF and RECURSE have compilation semantics and undefined interpretation semantics. This is evidence against assuming that full standard Forth is merely a uniform token evaluator.
3. Manfred von Thun, [An informal tutorial on Joy](https://hypercubed.github.io/joy/html/j01tut.html), revised February 2003: author-written primary language exposition hosted in a mirror; selectively read arithmetic/stack introduction, aggregate selectors, quotations, `ifte`, `primrec`, and `map` examples. Joy treats quoted programs as data passed to combinators, enabling higher-order composition without named formal arguments. `ifte` restores the pre-predicate stack before executing the selected branch. This is an informal tutorial, not a machine-checked specification or evidence about present implementations.
4. Abelson/Sussman/Sussman, [SICP §5.1, Designing Register Machines](https://mitp-content-server.mit.edu/books/content/sectbyfn/books_pres_0/6515/sicp.zip/full-text/book/book-Z-H-31.html), official MIT Press full text: selectively read GCD, register-machine notation, actions, subroutine continuation management, and stack-based recursion (§5.1.1–5.1.4); not the complete simulator implementation. Registers and a controller make state changes explicit; assignment, test, branch, goto, and operations express iterative processes. Nested/recursive calls require preservation of continuations and relevant register contents. The source also exposes the choice of what counts as a primitive: an assumed remainder operation may itself conceal a program.

## Candidate choice and burden

| Candidate | What a small composition mechanism buys | Where burden moves | Cycle-1 judgment |
|---|---|---|---|
| Lisp/Scheme-inspired expressions | Names, lexical procedures, quotation, lists, conditional calls and recursion compose arithmetic, symbolic transformations, text procedures and user-built abstractions. | Balanced delimiters, argument order/arity, variable scope, code/data distinction, recursive base cases. | Leading surface candidate: arguments and intermediate bindings are visible. Keep the dialect substantially smaller than Scheme. |
| Forth-inspired stack words | Flat sequences and named word definitions reuse transformations with little punctuation. | Operand order, hidden stack depth/type, stack shuffles and standard Forth's compile/interpret split. | Useful comparison condition; no reason yet to assume fewer punctuation tokens means lower context demand. |
| Joy-inspired quotations | Stack composition plus quotation/execution lets procedures manipulate or apply other procedures; list/text traversal can be ordinary combinators. | Remembering stack contracts and quotation/combinator behavior, especially saved/restored predicate stacks. | Strong alternative to raw Forth; avoid a large combinator vocabulary initially. |
| Register machine | Explicit state, jumps and primitive operations expose control and provide a natural trace. | Many instructions per abstraction; temporary names, labels and call/return bookkeeping. | Prefer as evaluator architecture/debug view, not the default authoring surface. |

These are comparative design hypotheses. No tokenization study, corpus-familiarity analysis, or controlled syntax experiment has been performed. Register machines were chosen as the third family; term rewriting has not been investigated in this scout.

## A bounded compositional kernel

Proposed surface: literals (integer, Boolean, text, empty list), names, `quote`, `if`, `let`, named procedure definition, lexical procedure values/application, and explicit durable-cell read/write. Arithmetic `+ - * quotient remainder`, comparison/equality, list `cons first rest empty?`, and text `length slice concat` form a compact useful base. Specify negative division, equality, indexing, text encoding and errors. These choices are a proposal, not a theoretically minimal basis.

Recursion plus selectors/constructors can derive traversal, mapping, filtering, folds and symbolic tree transformation; procedures can construct structured artifacts and consume earlier artifacts. Direct text primitives avoid forcing all useful string work through character-list encodings. Optional library seeds can save work while remaining inspectable ordinary definitions. A world consisting only of input/output examples or fixed task verbs would withhold this compositional leverage.

Persistent cells should hold typed values or versioned references to definitions/artifacts; procedure definitions remain inspectable source plus dependency bindings. Recursion and procedure composition must obey the same resource meter as built-ins. Cap total durable bytes, transient allocation, integer magnitude, call frames, output and evaluator steps. Charge bulk operations by processed size: one `concat`, equality comparison or multiplication cannot silently count as one cheap step regardless of operand size. Tail-call handling saves frames but does not remove time limits. Define whether budget exhaustion rolls back a transaction or leaves a resumable state; do not leave partial writes accidental.

These bounded semantics sacrifice unbounded computational universality. They can nevertheless permit many different algorithms within a finite budget. Language expressiveness alone does not supply persistence, consequence visibility or useful model behavior.

## Three strongest design implications

1. **Separate compositional freedom from task catalogs.** Supply data constructors, naming, procedure application and control, plus a small explicit persistence interface. This permits user-built domain abstractions instead of enumerating domain-specific actions. Start with the Lisp-like surface, retaining Joy as an empirical alternative.
2. **Make consequences reconstructible.** Each evaluation should expose result/error, selected state changes, resource use, and a bounded trace obtainable on demand. Definitions, bindings and artifacts must survive context loss and be discoverable by stable names. Register-machine-style state transitions inform this design; no source establishes that exhaustive traces fit a small model's context.
3. **Budget semantics, not just syntax.** Meter allocation and size-dependent operations as well as control steps; fix evaluation order and transaction behavior. A tiny instruction set can hide expensive primitives, while a tiny surface can hide stack or scope bookkeeping. Evaluate syntax validity, successful composition, reuse after context loss and resource failures separately before making any model-capability claim.
