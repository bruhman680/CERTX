# Cycle 2 — agency review of primitives and execution

Reviewed `CYCLE1_PRIMITIVES.md` and `CYCLE1_EXECUTION.md` in full. Research/design critique only; no model or execution experiment, installation, or primary-run access. Client date: 5 November 2026; host UTC date: 6 November 2026. No new primary-source claims are needed for these critiques; the reviewed notes already distinguish source support from proposed semantics.

## Judgment

A pure computational world can provide meaningful local agency: choosing projects, creating callable objects, testing consequences, revising them, and changing what future actions make possible. External filesystem/network access, plant simulation, biological metaphors, or a scalar reward are unnecessary. However, a programming language plus saved files is an affordance, not sufficient evidence of exercised agency. The proposed interaction loop must let the agent discover existing objects, select or abandon projects, observe effects, and extend useful work without an evaluator choosing every next target.

Both notes correctly reject persistence-as-learning claims. Their largest unresolved conflict is authoring surface: the primitives note favors Lisp-like expressions; the execution note specifies text assembly. A bytecode engine can implement a higher-level authoring language, but these are currently different proposed interfaces. Do not resolve that choice by calling assembly simpler: visible machine state can be easier to audit while requiring more model-generated instructions, labels, temporaries, and repair decisions.

## Three concrete counterexamples

**1. A self-chosen reactive drawing instrument becomes an integer-array exercise.** The agent wants a named instrument that accepts messages, maintains a pattern, and renders successive transformations. Lisp-like text/list/procedure values support a compact representation; an assembly-only interface with 256 instructions, integer cells, and 1 KiB output may force extensive encoding and leave nothing readily viewable. The attempted project could fail because of interface burden even if its underlying transformation is simple. This does not prove drawing, events, or first-class functions must be built-ins. Recommendation: adopt one canonical executable representation and compare a thin structured source language against direct assembly on equivalent capabilities. Offer inspectable text/grid/SVG-style output and a generic explicit `tick` or input-message call if needed; repeated invocations can supply temporal consequences without background processes. Keep the call interface stable across sessions. Audit rendered output as data and log inputs/state transitions.

**2. A useful construction repeatedly disappears at the fuel boundary.** A procedure incrementally builds an index over saved artifacts. Each invocation restarts from the initial state and hits the cap; atomic rollback discards the work. Increasing the cap changes the experiment, while the absence of progress might be misread as disinterest or inability to compose. Recommendation: keep atomic invocation but allow explicit guest-designed checkpoints: a successful bounded call can commit its cursor, partial index, and next-step procedure. Subsequent calls continue that algorithm using ordinary world state. This is distinct from host VM checkpoint/resume and needs no ambient authority. Make quotas observable before starting. Also distinguish 256 instructions *per procedure* from a 256-instruction ceiling on the entire reachable program: the latter can obstruct growing libraries even when every individual component is small. Specify composition/linking costs and dependency bounds rather than silently banning useful depth.

**3. A continuing seed stream manufactures apparent curiosity and improvement.** Every few turns the host offers a novel concept, rewards its visible realization, and removes old artifacts when the quota fills. The agent follows the stream. The final library looks diverse, but project choice is host-driven; forced deletion prevents testing long-term reuse. Improvement could come from richer hints, easier later tasks, or retrieval rather than changes in the fixed model. Recommendation: separate optional inspiration from required goals. Seeds should be declinable, revisitable, and unscored as instructions; disclose their schedule and whether the agent requested them. Compare finite initial seeds, continuing optional seeds, and no further seeds after onboarding. Treat seed-following, internally continued projects, and explicit assigned tasks as different observations. Give the agent inspect/rename/delete/compact/export capabilities within quota; expose available bytes and deletion consequences. Keep host audit storage separate and bounded so mandatory receipts do not secretly displace the agent's constructions. Do not automatically protect only evaluator-favored artifacts or prune unrecognized experiments.

## Strongest next comparisons

1. **Authoring burden under equal semantics.** Structured source versus assembly, with the same primitives, starting objects, interaction budget, model/context configuration, and interpreter limits. Report actual tokenizer cost, syntax/operand errors, repair success, executable completion, and cross-artifact calls. One comparison can match total model-token/compute budgets; another can match opportunities, but these answer different questions. No current evidence establishes the winner for 135M.
2. **Causal value of persistence.** After a common exploration phase, compare fresh contexts with the useful library, no library, and matched-size irrelevant material. Keep retrieval affordances and observation costs explicit. Use held-out inputs or new compositions to test useful reuse. Freeze both base and LoRA weights throughout; call gains external-library-assisted performance. If LoRA changes, that is a different condition.
3. **Choice and continuity under intervention.** Compare initial-only seeds, continuing optional seeds, and matched explicit goals; cross with generous versus tight visible storage. Record seed acceptance/decline, project continuation across fresh contexts, meaningful revisions after observations, dependency reuse, and behavior when a chosen project encounters a counterexample. An agent continuing a seeded project can be useful agency, but is not unprompted topic invention. Avoid claiming curiosity from topic counts, novelty scores, or fluent self-report.

Before those comparisons, settle discoverability, linking, checkpoint construction, quota ownership, and one source surface. These are experimental confounds, not reasons to expand the world into a domain simulator. A minimal viable world should make a variety of projects *possible and observable*; later evidence must establish what this particular fixed model can actually choose and accomplish.
