# Decoder, continuation and world-capability contacts

13 November 2026, America/Chicago. Live garden unchanged and paused at entry **1562**; original reference **1550** preserved. All findings below are detached. No model-facing change or proposed recovery mechanism was deployed.

- **Decoder/context:** eight fresh sampling replies, temperature .8/top-p .9, four fixed seeds on each of two exact saved contexts, cap 512. The early input produced one complete Python cell in four replies; the current-history input produced none, and all four ended naturally with unfinished fences. Both retained greedy references had zero complete cells. These are descriptive small-sample observations. Context length and content differ, so this does not isolate a cause. [Report](REPORT.md).
- **Actual consequences:** the sole eligible reply ran once, unchanged, on an exact matching world copy. It failed at multiprocessing semaphore creation with a read-only-filesystem error. Three operator-written isolation probes confirmed ordinary Python and a simple subprocess work, while Semaphore reproduces the failure. This is a specific environment capability mismatch, not evidence that all actions fail or that the program would otherwise succeed. No model was shown these results in the live garden. [Report](../decoder-consequence-contact-v1/REPORT.md).
- **Transparent continuation mechanics:** a 64-token suffix after token 256 matched exactly across the saved uninterrupted greedy run, an in-memory KV continuation and a fresh prefill of the exact raw token IDs. Maximum cached/fresh logit difference was approximately 5.34e-5 under the declared tolerance. A tokenizer-only test separately showed that reconstructing visible text can merge whitespace tokens and change the prefix. This supports careful continuation plumbing, not new memory capacity, durable KV storage or improved reasoning. [Scout and evidence](scouting/SCOUT.md).
- **Recovery design:** disposable Linux flock tests demonstrate live contention, release after abrupt process death, duplicated-descriptor lifetime, and the danger of unlinking a locked pathname. Persistent lock ownership and durable transaction history should have separate jobs. Existing exclusive-create writers do not honor flock; no drop-in migration or canonical lock deletion is authorized by these primitive results. [Design](../operator-lock-recovery-design-v1/DESIGN.md).

## Next strongest directions

1. A detached feedback branch can test whether the sampled action, when given its actual semaphore error, chooses a supported alternative. It must retain the sampled transcript and exact receipt, report every outcome, and not become a hidden task or live-history replacement.
2. A separately declared history comparison can ask whether current output depends on accumulated repetition. It must distinguish input length from content and avoid presenting edited history as unchanged continuity.
3. Before any durable chunk runner, specify last-token/cache/RNG/EOS invariants, capacity accounting, crash points and exact source pins. The current single in-memory greedy equivalence is a foundation, not a complete persistence system.
4. Recovery-protocol implementation remains an isolated operator project until ownership, legacy exclusion, concurrency and durability checks pass.

The strongest practical refinement adopted now is in **our observations**: distinguish decoder variation, complete syntax, actual dispatch, supported runtime facilities, and successful adaptation. No successful adaptation or general emergence was established in this contact. The newest separate Claude relay remains unidentified.
