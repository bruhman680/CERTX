## Useful extraction for our work

These are our design inferences, not additional published findings.

1. **Keep a recoverable base.** Treat specializations as candidates whose applicability and failure cases can be named. A tool that helps one task should not silently become a requirement for every task. A no-change result is useful.
2. **Locate the changed component.** Records can change available information; observation formats can change its accessibility; tools can change permitted operations; routing can change which procedure runs. Their effects may interact. Do not label the combined gain as memory or reasoning improvement without separating them.
3. **Select using evidence available at decision time.** A known failure in a saved trajectory can justify a targeted repair. A task label or self-reported confidence alone does not establish that failure. Base execution, router calls and rejected attempts must count toward budget.
4. **Preserve derivation separately from navigation.** Our current maps can remain editable. Preserve original parent revisions, candidate edits, run configurations, evidence and superseding assessments in the historical record. A tidy display tree is neither an immutable event ledger nor a causal dependency graph.
5. **Repeat candidates before promotion.** Separate noisy selection from sealed confirmation. Repetition reduces uncertainty about a sampled configuration; it does not by itself remove selection bias, shared-source dependence or evaluator defects.
6. **Assess observation losses.** A compact interface should preserve what the current decision needs, including useful contradictions and provenance. Faster retrieval that hides a relevant discrepancy can be a regression.

The optional [evidence-triggered specialization](../../modules/evidence-triggered-specialization.md) adds this to our existing bounded loop without changing core prompts, schema or scientific verdicts. The record is usable guidance now; its behavioral benefit remains an open test.
