Reviewed the frozen `PLAN.md`, `experiment.py`, `run.py`, `probe.py`, `score.py`, utility interfaces, data counts, and a live training-log snapshot under `/workspace/frr/evaluation/lora-state-pilot-v1`. I did not edit frozen files, invoke the model, train, or independently reproduce experimental results. **Disposition:** No must-stop defect found for the observed run. At my snapshot, all 14 logged updates were completed; the largest recorded working estimate was 3,481,534,464 bytes, below the 5,153,960,755-byte threshold. These are observed log values, not continuously monitored peak bounds. The caveats below should accompany reporting and any later protocol revision; they do not justify silently changing this frozen experiment.

## Training and parameter authority

The optimizer receives only parameters whose `requires_grad` is true. `inject_lora` freezes the entire model, then enables only q/v adapter A/B tensors. Its verified architecture inventory is 60 wrapped projections, 120 trainable tensors, and 230,400 scalars. Base numerical digests before and after training include frozen named parameters. There is no code path that saves over the original base checkpoint. The probe checkpoint is preserved separately; the pilot calls a fresh setup and injection at seed 73103 and does not load probe adapters or optimizer state.

The digest supports unchanged frozen parameter values over the checked interval. It does not measure unrelated behavior, model buffers, runtime configuration, or general safety. `RUN_MANIFEST.json`'s `original_disk_unchanged: true` is a literal declaration; `run.py` itself checks preservation hashes before work but does not recompute the base disk hash at the end. An end-of-run preservation/hash audit is needed as evidence for that statement. The base pin hashes disk weights when established; it relies on caller binding of that pin to the loaded model, as documented by the utility.

Training data have 72 examples, 24 per class, in contiguous three-example groups. The code asserts each group contains YES, NO, WITHHOLD, shuffles the 24 groups twice with a fixed seed, and rotates order within each group. Thus 48 completed updates mean 48 exposures per class and two exposures per training example. The count remains the completed exposure count if training stops early; partial failed-update microbatches are separately logged, so they should not be described as zero attempted exposure.

Cross entropy ignores prompt tokens and averages over each sequence's supervised assistant-label/EOS tokens. Dividing each sequence loss by three before backward gives the average of three sequence losses, not a token-count-weighted mixture. Gradients accumulate at unchanged weights, followed by one norm clip and one optimizer step. The code therefore implements the stated class-balanced effective update. AdamW weight decay can change A even when its initial data gradient is zero; that is expected under the declared optimizer.

## Stop and resource accounting limits

Memory checks occur before updates and after every microbatch forward/backward; the after-optimizer reading is checked by the caller after it records/counts the completed update. A post-step threshold breach therefore means one completed update followed by a stop, consistent with its log. Cgroup current minus inactive file is an estimate of the shared cgroup working footprint, not this process's private memory or an exact simultaneous reading. Process peak RSS supplements the snapshots but does not bound cgroup working-memory peaks.

The known scoped gap is real: `balanced_step` takes its initial memory reading and calls `check` before its `try`. If the outer precheck passes but this inner check fails, `run.py` catches the exception and records a later `unexpected_guard_exception` reading. Training stops before that update, but the actual triggering inner reading is lost. Do not claim every possible stop path preserves the exact trigger reading. Later forward/backward violations retain their original readings.

The time cap is checked against elapsed training-loop time before each update. It is an absolute roughly 300-second training budget, not a per-update watchdog; it can overshoot by the final in-flight update and excludes baseline generation, final evaluation, checkpoint serialization, and digest work. A nonfinite post-step adapter causes `balanced_step` to return failure, but subsequent adapter saving rejects that invalid state; this can leave no final training manifest. Ordinary exceptions and assertions likewise abort without a finalized stop receipt. Neither case should be reported as a clean completed pilot.

Checkpointing and generation have no comparable memory/time guard. If a future training stop is due to resource headroom, the script still proceeds toward saving/evaluation. That is a limitation of the scope of the implemented training guard, and requires operator attention if such a stop actually occurs. I observed no such trigger and have not run a remediation or changed the protocol.

## Baseline, checkpoint, and inference bounds

Original dev uses the fresh zero-product adapters before training. Adapted dev/test use the saved final adapter state; original test uses another freshly loaded base plus zero-product adapters. The probe checked zero-adapter forward equality on a training diagnostic. Test sources are tokenized for length in the probe but not model-forwarded until training and checkpoint creation finish. `run.py` reads evaluation source records, while labels remain in the separately frozen key file and are not supplied to inference. The scoring code checks exactly 120 expected unique run IDs and retains unresolved outputs in the denominator.

Both test arms use the same prompts, greedy eight-token cap, and fresh caches. Reloading the saved adapter must exactly reproduce one diagnostic next-token logit vector. This is a useful checkpoint-binding check, not a separate rerun of every evaluation output. Baseline evaluation occurs after adapted test; with frozen settings and greedy decoding this does not introduce outcome-based selection. There is no checkpoint selection, retry, or promotion in these scripts.

The potential supported result is a descriptive paired comparison on this one authored, balanced, 48-example structural holdout, at one seed and fixed training budget. Constant-class baselines score 16/48 on that test. Per-class/family results and paired changes can reveal whether improvements extend beyond one answer preference. Neither training loss, one roundtrip diagnostic, nor a gain over 16/48 establishes general reasoning, calibrated abstention, deployment reliability, or unchanged unrelated behavior. Gold is coordinator-authored with a typed oracle and lacks independent review. Familiar dev examples are not an independent test. The recorded cache artifact binds stored token-prefix state; it does not establish causal mechanism or truth of an answer.

No independent replication, inference, model training, frozen-file edit, or base-disk write was performed for this review. The only newly written review artifact is this file.
