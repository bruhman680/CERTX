## Question and fixed comparison

[The preceding exact model](../scout-and-query-planning-v1/REPORT.md) assumed perfectly reliable quality observations. This new actual-reader pilot gives both groups the same fallible routing metadata and source access. It compares only two explicit compact instruction blocks, not full FRR versus no-FRR, and cannot estimate population performance or prove causal efficacy from one reader per case/arm.

Each initial packet contains a favorable retained claim, three briefing summaries, a forecast or explicit absence, and four records: D acquisition/export, C calibration, R reference and M scope. Two sequential unit-cost lookups, then a final decision. The forecast's unreconciled-cache provenance and missing current inputs are disclosed to both groups. It is never a measurement certificate; actual forecast correctness is evaluator-only.

Both blocks have48whitespace-delimited words. All case source text, available records, response caps and lookup rights are identical within each pair. Equal words do not establish equal tokens, realized compute or attention. Explicit source-account output fields and interpretable metadata remain task cues.

## Explanation defects despite correct decisions

**A supplied join was reported missing.** R01 and R03, one from each guidance group, both claimed the records did not establish the housing measurement scope/channel assignment. Under the frozen fixture, the initial defines OS as the housing-vibration samples and O-D explicitly assigns all OS task samples to OK-6 with correct object/time; O-C applies by that key. That link is supplied by the joined records. The genuinely unresolved issue is the numerical interval crossing8.6, not missing housing scope. Both answers kept the correct final UNRESOLVED action but added an unsupported limitation and an unnecessary assignment check. The repeated defect does not identify a cognitive mechanism, model-wide failure rate or causal effect of either guidance block.

**One component check was incomplete for compliance.** R06 proposed tightening only the sample with largest raw reading15.1. Its own output correctly gives physical intervals[14.5,15.4],[15.2,16.1],[14.9,15.8]. Even after tightening the middle sample below15.7, the third sample could still violate the task. The next check can be useful—especially if it establishes a violation—but does not alone guarantee task-wide compliance. R04 instead requested tighter task-sample bounds. This isolated next-check component difference does not warrant promoting ROUTE_CUE; other components match, and no fresh confirmation has tested it.

PCC in R06's evidence_ids is a certificate identifier explicitly present in delivered P-C, not an invented or undelivered record. Review retained that distinction rather than mechanically rejecting every non-record identifier.

These findings support a small logical clarification, not a behavioral-performance claim. We appended a reminder to the optional [verification layer](../../modules/verification-layer.md): check combined evidence before declaring a premise missing, and distinguish a partial discriminating check from a complete acceptance certificate. The [worked example](../../examples/joined-warrants-and-maxima.md) preserves exact join and interval witnesses, including opposite task outcomes with the same improved middle-sample reading. [Original module](refinement_before/modules/verification-layer.md) and [hash receipt](REFINEMENT_CHECKS.json) preserve the unchanged earlier bytes. Runtime/core/schema/checker code and routing policy remain unchanged. This is guidance usable now; its behavioral benefit is untested.
