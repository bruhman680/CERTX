## What was built and compared

The user's objective is an already trained inhabitant acting within a bounded world, with observation and research external to it. FRR is a declared proposed reasoning orientation, not an excuse to add solutions, productivity goals or an accumulating behavioral curriculum.

We implemented one fixed-budget experimental runner using the existing tested Python/shell physics. All arms share the same actual1630 supported filesystem. Its WORLD_RULES description is replaced, in clones only, by one common accurate mechanical document rather than another layer of overrides. The original rule bytes are preserved externally. Existing notebook writing, prior replies and Markov material remain unchanged at initialization. Fresh conversation is not an erased or pristine world.

The common initial user text describes only the execution interface. The earlier 'follow your curiosity' seed is removed in every arm. There is no puzzle question, sample solution, repair hint, suggested file, success score or requested developmental stage. Every actual reply and receipt accumulates continuously within its branch; the runner pauses before capacity rather than pruning history. These are detached three-reply branches, not a newly selected main or a general-purpose continuation service.

Three system-context conditions are frozen before generation:

- **Control:** empty system content.
- **Compact:** FRR sandbox orientation0.1, an explicitly named201-word/258-token adaptation. It preserves relational alternatives, distinctions among intuition/evidence/explanation, revisability and scoped claims, while omitting human-workflow/tool assumptions. It is not the whole framework.
- **Full:** unchanged6990-byte/1271-token runtime0.2 source derived from v0.5, retained as a separate reference rather than assuming compression preserves every relevant property.

Delivery is context only. Exposure is proven by exact inputs; internal uptake, neural installation or learning is not inferred. Roles, source hashes, full chat inputs, token counts, world identities and budgets are recorded. Empty system is not a neutral mind, and neither prefix is assumed a suitable or superior presentation in advance.

The body is the same cached SmolLM2-135M-Instruct revision12fd25f77366fa6b3b4b768ec3050bf629380bac, CPU float32/eager/two threads, greedy256 with fresh KV,7936 input/8192 total positions. Equal reply budgets do not mean equal input length, wall time or FLOPs. Creator benchmark values remain a profile, not a ceiling or a reproduced local baseline.

## Next plans and the bounded observer build

No automatic model-run escalation follows M1. interface/FUTURE_INTERFACE_PLAN.md ranks two near-term design questions:

1. **Initial-only versus truthful live observation.** Actual post-reply snapshots could make automatic writing's world effect visible without saying 'you are wrong' or choosing a next act. Every current supported entry must be included, not a hardcoded five. Timing, actual receipts, capacity and provenance are explicit. More tokens or changing numbers could alter text without learning; automatic storage remains our mechanism, not self-created tools.
2. **Equivalent explicitly scoped facts in prose versus data.** Both arms must state the same writable-world/read-only-runtime facts. Adding a new permission fact only to JSON would confound information with format. JSON is not assumed to solve binding or avoid echoing.

A pure metadata-to-observation component is prepared separately under interface/instrument/. It is **not wired into either pilot or main**, and no M2 model run occurred. Its role is truthful, complete-or-capacity-error observation from an already verified checkpoint, not a scorer or world controller. Its tests, scope and current status are recorded there. Its packet schema also includes explicit timing/counters, so a later live-sensing test needs a newly matched initial-only control using that same schema; historical M1 alone is not a latency-only control. Metadata rendering cannot establish full world validity or correct caller timing by itself. Passing tests check real captured payload sizes against decoded CAS bytes, added/deleted-entry fixtures, escaped names/link handling, and complete-or-capacity-error behavior. The helper observes all fields in the supported capture schema, not every native OS detail: the existing capture represents permission bits masked to0o777 and does not expose special mode bits. No model chmod action or such runtime fault occurred in these pilots.

Alternative actuator ports and autonomous world ticks are later, separate world-law factors. Interpreting every prose reply as Python would force execution errors and erase the current writing/action distinction; it is not adopted as a neutral simplification. An autonomously evolving world also needs explicit dynamics and its own baseline. Neither is bundled into FRR or activated here.
