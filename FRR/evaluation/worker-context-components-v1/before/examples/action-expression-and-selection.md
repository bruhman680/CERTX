# Distinguish action expression, selection and execution

Optional method note from [the finite-action contact](../evaluation/reader-action-choice-v1/REPORT.md). Supplying a new tool or menu creates an affordance; it does not establish that a model can express the request, choose it when useful, interpret its result or manage uncertainty.

Observe these separately when relevant: free output format, any constrained-decoding policy, appropriate conditional action selection, actual tool traces and outcomes, worker readout, supported final answers and costs. Preserve invalid actions and unhelpful choices rather than silently replacing them with a successful route. A forced-choice decoder is a usable policy mechanism but does not establish free-format competence. Its semantics and presentation robustness still need tests.

A model returning an insufficient-evidence action differs from a tool failing and the controller then producing an unknown terminal. A semantic missing-value answer differs from both. Likewise, copying a requested action word does not show knowing when to choose it. Counterbalance code assignments and presentation order where useful; validity alone can hide a constant or layout-driven choice.

Repeated visible prompts across different hidden worlds do not create independent reasoning samples. Record deduplicated router probes, actual tool requests, worker cache reuse and logical routes separately. Nominal tool costs, measured latency, token counts and financial charges have different meanings. A simple observed-input rule provides a useful comparator without turning the exploration into a competition.

The current example has a finite designed menu, one retrieval budget and a known toy grammar. It does not expose internal reasoning or establish unrestricted autonomy. An interface failure can motivate a separately recorded new interface or lesson; it does not automatically block other exploratory paths or retroactively change an earlier result.

Immediate-action tests also differ from allowing planning, additional turns or longer public output. A failed eight-token selection interface does not establish how the model would behave with more deliberation room. Vary planning allowance separately from examples or training so their effects remain interpretable.


## Descriptions, examples and unused allowance

The [planning/examples contact](../evaluation/planning-and-examples-v1/REPORT.md) preserves a strict command failure alongside a post-run semantic readback: “Report insufficient evidence” is recognizable as the offered UNKNOWN description, although the formal decoder rejects it. Do not equate parser rejection with absence of an uncertainty expression. Declare any accepted aliases prospectively, countertest opposite/negated phrases, and preserve original strict results. Recognition alone does not establish calibrated uncertainty or correct conditional use.

A larger output cap provides no extra generated steps if the model ends early. A request for a public plan is not evidence that a plan was produced or used. Worked examples can change output format, length and order cues together; counterbalance them before calling a new response pattern robust policy learning. Preserve deferrals with accessible evidence separately from warranted unknowns and successful answers. These are optional diagnostic patterns, not a new default decoder or mandatory gate.


## Declared descriptions and observation/action roles

The [description/rule contact](../evaluation/descriptions-and-rules-v1/REPORT.md) implements a narrow declared phrase interface with positive/negative cases. Preserve last unsupported/negated declarations instead of reviving an earlier valid command. This is a limited command language, not fuzzy semantic interpretation or a general intent detector. Fixture success and historical coverage improvements do not establish a gain on fresh model outputs; in that contact both decoder views chose the same actions on all new replies.

Rules stated in a prompt, worked demonstrations and rules executed by a controller are different mechanisms. Counterbalance rule/example order and report transfer failures before calling one favorable request a learned policy. A response such as “no visible record” can be a provisional observation without an executable action. A checked observation could feed a separate controller; preserve who supplied each step and do not attribute delegated control to the model. Broader exploration need not wait for this small router to pass.
