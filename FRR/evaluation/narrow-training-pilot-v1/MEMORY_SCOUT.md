# Memory feasibility follow-up: LoRA

Context supplied by the pilot runner: full-weight AdamW was planned for 48 steps and stopped by its predeclared memory-headroom guard after one step. The partial checkpoint was preserved; no second training attempt was made in this run. This note proposes a future feasibility check, not a change to that result.

**Primary source:** Hu et al., [LoRA: Low-Rank Adaptation of Large Language Models](https://arxiv.org/abs/2106.09685), [version 2 full text](https://arxiv.org/html/2106.09685v2), checked 2026-10-30. **Read depth:** abstract, introduction’s memory rationale, and section 4.1; not a full experimental or appendix audit.

LoRA freezes an original matrix W₀ and trains a factorized update BA. For a d-by-k matrix, the two factors contain r(d+k) parameters, instead of dk, when the rank r is small. Only the factors need parameter gradients and optimizer state; the paper explicitly attributes memory savings to avoiding these for most original parameters. Its forward pass still contains W₀x + BAx. These claims support a mechanism for reducing memory, not a memory estimate for this machine. The paper’s GPU savings do not establish corresponding CPU savings.

**Engineering inference for this pilot:** freezing the backbone does not remove its resident weights or its forward computation. Training adapters within multiple layers still requires backpropagating through the intervening computation to obtain adapter gradients. Relevant activations and temporary buffers therefore remain, with their actual memory depending on batch size, sequence length, dtype, checkpointing and implementation. Reducing trainable parameters need not reduce total peak memory by the same proportion. AdamW should receive only parameters marked trainable; otherwise a nominal “LoRA” setup could obscure the intended accounting.

**Next feasibility question:** would a specified low-rank adapter configuration on SmolLM2-135M-Instruct stay above the same headroom threshold through forward, backward and the first optimizer-state allocation at the intended sequence length? Before another substantive run, count actual trainable parameters and measure peak process/container memory for that configuration under a separately declared small feasibility budget. Distinguish static parameter/optimizer estimates from observed peak memory. This is an untested proposal, not a guarantee of fit or learning quality; it does not authorize or imply another training attempt in the completed run. No packages were installed and no frozen scout or FRR files were edited.
