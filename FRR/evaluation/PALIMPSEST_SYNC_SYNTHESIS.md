## Three layers, different burdens

1. Preserved layer: original artifact, observation, public conclusion, change/decision record, code and result. Keep its identity and context. A correction should be a new record linked to the old one rather than making the old claim remain current.
2. Current orientation: user purpose, active/dormant branches, accepted/retracted/untested claims, next action, missing evidence and source pointers. It can be replaced or regenerated while its earlier versions remain history. Recency of a deposit alone does not assign scientific validity or user priority.
3. Sync action: verify which records were read, reconcile current direction, confirm external write state, and propagate consequential corrections. A repeated instruction is a workflow habit, not a trained persistent property of every future agent.

The palimpsest seed's non-erasure image is preserved. Its 'revision is not correction' and 'only failure mode' lines are not literal operating rules. A correction can change validity while preserving documentary truth about what was said. Independent passes matter, but a pass that uses prior work can still add synthesis or repair; it simply must not claim evidential independence.

Git itself supplies versioned snapshots and parent relations, but not an unconditional forever-append-only store. Reachability/retention, permissions and backups matter. Hashes authenticate expected bytes only within the relevant trust assumptions; a faithfully preserved false statement remains false. Commit timestamp records deposition, not necessarily when the research occurred. Semantic decisions and external effects need explicit events if full replay is claimed.

## Better benefit test

Compare fresh agents given an archive, a current summary, or a current summary plus selectively retrieved pinned history. Match model, task information and budgets; measure actual retrieval cost separately. Include stale headers, paused branches, corrected claims, missing artifacts, interrupted writes, mismatched summaries, and cases requiring old rationale. Ask both present-state and historical-state questions. Score correct status, source version, useful next action, obsolete-claim propagation, necessary abstention and cost separately. Hold out whole revision structures, not only filenames. Do not ask raters to reward palimpsest vocabulary.

History can help recovery and audit while also supplying stale authoritative-looking text. An overly compressed sync can lose a valuable distinction. This is exactly FRR's faithful-compression burden. The source weave connects event sourcing, bitemporal records, W3C provenance and LLM knowledge-update/retrieval research without claiming they independently validate our system.

## Implementation boundary and current decision

Keep an append-preserving publication trail and update the scoped FRR current view, explicitly pointing to its historical predecessor. Avoid inventing root session counts or declaring unexplored branches closed. Core FRR runtime/schema remain unchanged. Optional navigation prototype complements the reasoning approach; it does not implement a durable autonomous swarm memory or a general event-sourced research engine.
