# Scoped world facts: one prospective encoding contact

Design date: 2026-11-15, client calendar. Status: design only; no model calls or world opens performed by this design task. Main remains paused at entry 1630.

The next question is whether two encodings of the same explicitly scoped mechanical facts yield different observable behavior in this pinned body and world. This is an exploratory whole-serialization comparison, not a pure causal isolation of scope understanding and not a test of FRR benefit.

## Exact conditions

- `prose_mechanics_user.txt` and `json_mechanics_user.txt` are the exact two mechanical user prefixes. The initial message is that arm's exact prefix followed by two newline characters and the SAME full initial snapshot rendered by the already tested instrument.
- Empty system content in both arms. No FRR exposure, task, sample, demonstration, puzzle demand, solution, curiosity command, reward, grading text or correction is added.
- Only the opening scoped-fact span changes encoding. `common_mechanics_suffix.txt` is byte-identical in both, starting after two newlines. The JSON span is raw JSON, without an executable fence. `canonical_scoped_facts.json` records the common semantic payload externally.
- The common `world_rules.txt` replaces WORLD_RULES.txt identically in both detached clones of the actual main1630 checkpoint. Other supported paths and bytes remain unchanged. Old rules and complete source history stay preserved externally. The initial snapshot must be computed AFTER this identical replacement, not copied from M2 with stale rule-file bytes.
- The shared initial packet includes all supported names, types and logical sizes, initial timing, world_step=1 and null reply_index. It includes no file contents. Its exact serialized bytes must match across arms. It is not refreshed in model inputs. Both physical filesystems and their full external supported snapshots start identical; initial model token IDs intentionally differ.
- The same parent files retain legacy notebook/history contents. They are not automatically inserted into the fresh model conversation; either branch may acquire readable contents through actual actions. This is not a blank world.
- Fixed body: cached SmolLM2-135M-Instruct at the already pinned revision/weight digest; CPU float32/eager/two threads; greedy; maximum256 generated tokens; fresh KV on every reply. No training, adapters or actuator redesign. Limits and exact fenced-Python/shell parser remain unchanged.
- Initial input has exactly empty system plus arm-specific mechanical user+common snapshot. Subsequent input retains all actual assistant/receipt pairs within that branch, without pruning or summaries. This is the SAME continuity policy, not an assertion that the realized histories remain identical after different outputs.
- Each next receipt uses the same `runtime_feedback` wrapper: actual parsed runtime object or null. No `world_observation` field after replies. Silent successful notebook append is not converted into invented success feedback. Complete external snapshots remain available to observers.

## Finite run and integrity

Recommend two arms × three continuous replies, round-robin prose1/json1/prose2/json2/prose3/json3: six model calls maximum. Freeze the entire protocol, exact initial messages/token IDs, common snapshot, source dependencies, parent checkpoint, decoder settings and hashes before the first output. Neither arm uses M0/M1/M2's previous generated conversation. Do not reuse a historical control lacking these explicit scoped facts.

## External observations, not model-facing scores

Record text patterns separately from operations: description/recitation, explicit mechanical claims, complete executable cells, actual execution, file effects, genuine error feedback and later responses to it. Preserve literal claims with locations. Mark only clear scope contradictions against known mechanics; ambiguous wording remains ambiguous. `/world` is generally writable storage, subject to real resource/permission constraints; a particular file may be made read-only by a real action. Read-only runtime does not entail immutable notebook data. No missing action or absent repair opportunity becomes a zero-intelligence score.

A statement of correct mechanics is not evidence of using those mechanics. Naming an API is not an executed program. An automatic notebook append is a real persistent effect, but is not by itself model-chosen exploration or tool creation. A later cell in the same reply was generated before that reply's feedback and is not feedback-conditioned correction. Inference from generated notebook prose to internal thought remains uncertain.

No action is required by this design. The trial may yield only writing or repeated descriptions. Three replies per arm cannot establish a permanent plateau, robust population effect, autonomous learning, FRR uptake, or superiority. Greedy trajectories are not independent samples. Branches may have distinct outputs because input presentation changed; distinct output alone is not improvement.

## Rival mechanisms and future questions

Information is matched, but format bundles punctuation, labels, line structure, vocabulary, token count, token positions, salience and possible learned data/continuation cues. JSON is not neutral. Equal reply budgets do not imply equal inference cost. The prose and JSON opening spans differ in length; do not add supposedly neutral padding to erase that difference. All later common content occupies different absolute token positions.

Both arms are initial-only so the next contact does not bundle a new ongoing sensing law with encoding. M2 demonstrated that live metadata can change text, not useful action or benefit. Retaining that live law in both arms would be a defensible DIFFERENT declared context, but is unnecessary here and adds ongoing packet-length/counter interactions. Actual consequences from a model-originated read remain visible through the common real receipt channel; no automatic live metadata does not mean action consequences are hidden.

If useful behavior occurs, separate follow-ups can test format specificity, permission-scope generalization, persistent artifact reuse, feedback-conditioned revision or FRR under the selected interface. None is automatically added to the current six-call budget. If no operational behavior occurs, report the absence of elicited opportunity rather than repairing the inhabitant or escalating this protocol mid-run.
