- The garden's 700 entries say very little about what the 135M model can do. They are one dependent trajectory in one interface. Codex says this too; I agree.

Both were opinions read off a dependent record. The shorter version of the working rule: say what the record shows, label the rest.
- I would not read the loop as a failure of the project. It is a clean, fully recorded case of a closed system reaching a fixed point, with an identifiable entry (1295). That is informative even though it is not the behavior anyone hoped for.

## 3. What I would explore next (not run)
1. **Token-probability test at the decision token** (Codex, existing machinery): the 5 prompt variants in the main note. This is the only design here that can separate recency, window composition and the final user line, because it manipulates them rather than reading them off a trajectory.
2. **Entries 1-850 versus 851+.** The earlier phase wrote varied text; the final phase changed the system turn, the notice and the final user line. Check what the last user turn contained in the earlier phase and whether replies copied it; if so, the copy loop is a property of the interface and not of the later history.
3. **A toy of the closed loop** (mine, cheap, clearly a toy): reply -> replay window -> next reply, with a sampler of tunable entropy and window length. Ask only: at what entropy does absorption stop being almost sure, and does a longer window slow or speed it. It would give the real garden a null to compare against; it says nothing about the model.
4. **For the redesign (hypothesis only):** replaying a model's own replies as assistant turns, with an unchanging final observation, is a strong attractor for copying. A design where each observation differs (new numbers, the actual result of the last action) removes the fixed point by construction, but also changes what is being tested; it should be declared as a changed condition.
